# 상세페이지 자동화 시스템 — 단계별 개발 프롬프트

버전: HAO Detail Automation Prompt v2  
작성 기준: 고객 DB 접수부터 관리자 검수, Codex 기반 기획·이미지 생성, 촬영 레퍼런스, 상세페이지 제작, 피드백·납품까지

---

## 먼저 고정할 운영 원칙

이 문서에서 말하는 “API를 사용하지 않는다”는 **OpenAI API를 호출하지 않고, 관리자 개인의 Codex/ChatGPT 사용량 안에서 AI 작업을 실행한다**는 뜻입니다.

고객 자료를 여러 컴퓨터에서 저장·조회하기 위한 로그인 서버, 데이터베이스, 객체 스토리지의 통신 API는 별도로 필요합니다. 이것은 AI API가 아니라 업무 시스템의 저장·인증 기능입니다.

웹 관리자 버튼이 Codex 구독 재화를 서버처럼 직접 호출하는 구조는 전제로 삼지 않습니다. 1차 운영 방식은 다음과 같습니다.

1. 관리자툴이 승인된 고객 DB를 `Codex 작업 패키지`로 생성
2. 관리자가 Codex에서 해당 작업 패키지를 실행
3. Codex가 웹 검색, 파일 분석, 기획안 작성, 이미지 생성, 폴더 저장을 수행
4. 관리자툴이 생성 결과와 상태 파일을 다시 읽어 화면에 반영
5. 추후 공식적으로 지원되는 계정 기반 Codex 자동 실행 방식이 확인되면 무인 실행 단계를 별도로 추가

OpenAI API 키 입력창, 공개 HTML의 API 키, 브라우저에서 `api.openai.com`으로 직접 보내는 요청은 만들지 않습니다.

# 1. 목표와 자동화 범위 정의

## 설명

가장 먼저 상세페이지 제작 과정에서 자동화할 범위와 사람이 반드시 검수할 범위를 구분합니다.

핵심 목표는 고객이 전달한 DB를 잃지 않고 정리하여, 관리자가 어디서든 검수하고, 승인된 사실과 레퍼런스를 바탕으로 기획안·촬영 레퍼런스·상세페이지 시안·최종 제작물을 단계적으로 생성하는 것입니다.

AI가 고객의 사실을 임의로 바꾸거나 완성품을 무검수로 납품하는 구조가 아니라, 관리자의 승인 지점이 명확한 제작 운영 시스템을 만듭니다.

## 프롬프트

```text
넌 상세페이지 제작 자동화 시스템을 설계하는 시니어 프로덕트 아키텍트이자 제작 실무자야.

우리는 다음 과정을 자동화할 거야.

- 고객이 고객 작성폼에서 제품 데이터, 텍스트, 사진, 영상, 로고, 스펙, 인증자료, 레퍼런스를 제출
- 제출 원문과 파일을 서버에 안전하게 저장
- 같은 자료를 고객 브라우저 IndexedDB에도 임시 안전본으로 저장
- 관리자 로그인 후 어느 컴퓨터에서나 프로젝트와 파일을 조회
- 고객 원문을 정규화해 1차 제품 내용정리본 생성
- 관리자가 미기입, 사실, 수치, 인증, 금지 표현을 검수하고 승인
- 내부 상세페이지 제작물, 제작 전 기획안, Figma 시안, 촬영 레퍼런스, 웹 검색 레퍼런스를 분석
- 승인된 DB를 기반으로 A/B 기획 방향, 상세페이지 구성안, 촬영 시안과 이미지 생성 프롬프트 제작
- OpenAI API는 사용하지 않고 Codex 작업으로 이미지와 문서를 생성
- 생성 결과를 업체별 폴더에 저장하고 관리자툴에 다시 연결
- 고객 피드백, 수정, 내부 검수, 최종 납품까지 버전으로 관리

먼저 전체 시스템을 고객 영역, 업무 서버, 관리자 영역, Codex 작업 영역, 파일 저장 영역, 고객 확인 영역으로 나눠 설계해줘.

반드시 다음을 구분해줘.

1. 완전 자동화 가능한 단계
2. 관리자 승인이 필요한 단계
3. Codex에서 사람이 실행해야 하는 단계
4. 서버가 필요한 단계
5. 브라우저만으로 가능한 단계
6. 개인정보와 고객 원본 때문에 공개하면 안 되는 항목

구현 전에 전체 폴더 구조, 데이터 흐름, 상태 흐름, 권한 구조, 실패 복구 흐름을 먼저 제안해줘.
```

## 체크포인트

- 고객 접수부터 납품까지 범위가 포함됐는가
- AI 작업과 일반 서버 기능이 구분됐는가
- 관리자 승인 단계가 명확한가
- Codex를 공개 웹서버처럼 직접 호출한다고 가정하지 않았는가
- 고객 원본과 공개 자료의 경계가 정의됐는가

# 2. 사용자 역할, 로그인과 권한 설계

## 설명

고객 DB를 여러 관리자가 어디서나 관리하려면 단순한 링크 공유가 아니라 실제 인증과 권한 관리가 필요합니다.

고객, 관리자, 디자이너, 포토그래퍼, 최고관리자의 권한을 분리하고 모든 조회·수정·삭제·다운로드 기록을 남깁니다.

## 프롬프트

```text
상세페이지 자동화 시스템의 사용자 인증과 권한 구조를 설계해줘.

사용자 역할은 아래와 같아.

- 고객: 자신의 프로젝트 작성, 파일 업로드, 진행상황 확인, 피드백 작성
- 관리자: 접수 확인, 내용 수정, 검수 승인, Codex 작업 생성, 고객 피드백 관리
- 디자이너: 승인된 기획안과 생성 시안 조회, 디자인 파일 업로드, 수정본 등록
- 포토그래퍼: 촬영 시안과 컷 리스트 조회, 촬영 결과 업로드
- 최고관리자: 계정 발급, 권한 변경, 프로젝트 삭제, 감사 로그 확인

구현 조건:

- 관리자 페이지는 로그인 없이는 열리지 않게 하기
- 비밀번호를 HTML, JavaScript, GitHub에 하드코딩하지 않기
- 비밀번호는 서버에서 안전한 해시로 저장하기
- 세션 만료, 로그아웃, 비밀번호 재설정 지원
- 프로젝트별 접근 권한 분리
- 고객은 예약번호 또는 프로젝트 코드와 추가 인증값으로 자신의 프로젝트만 조회
- 영구삭제는 최고관리자 재인증과 프로젝트명 재입력을 모두 요구
- 로그인 실패 횟수 제한과 감사 로그 남기기
- 파일 다운로드는 만료 시간이 있는 서명 URL로 제공
- 공개 GitHub Pages만으로 보안 로그인을 구현했다고 표현하지 않기

DB 테이블, 인증 흐름, 화면 구성, API 엔드포인트, 보안 테스트 항목까지 제안해줘.
```

## 체크포인트

- 관리자 인증이 서버 기준으로 작동하는가
- 역할별 권한이 분리됐는가
- 고객이 다른 프로젝트를 볼 수 없는가
- 영구삭제와 파일 다운로드가 보호되는가
- GitHub Pages의 공개 한계를 숨기지 않았는가

# 3. 고객 작성폼과 입력 DB 설계

## 설명

고객이 입력한 내용은 이후 모든 결과물의 사실 원본입니다.

예시 문구나 placeholder를 작성된 값으로 처리하지 않고, 미기입·자료없음·확인 필요 상태를 필드별로 기록해야 합니다.

## 프롬프트

```text
상세페이지 고객 작성폼과 프로젝트 DB 구조를 설계해줘.

수집 항목:

- 고객사명, 브랜드명, 담당자명, 연락처, 이메일
- 제품명, 카테고리, 판매 채널, 타깃 고객
- 한 줄 제품 설명, 핵심 장점, 차별점, 구매 혜택
- 제품 옵션, 용량, 구성, 판매가, 배송 정보
- 원재료, 영양정보, 원산지, 제조 방식
- 인증, 시험성적, 특허, 납품 실적과 증빙 상태
- 반드시 포함할 문구
- 절대 쓰면 안 되는 표현
- 원하는 디자인 무드, 색상, 구성
- 참고 링크와 경쟁사 링크
- 제품 이미지, 누끼 이미지, 로고, 스펙, 인증서, 영상, 참고 이미지
- 제작 범위, 예상 분량, PSD 제공 여부, 바리에이션 여부
- 고객이 진행상황을 확인할 프로젝트 코드

각 필드는 아래 메타데이터를 가져야 해.

- value: 실제 입력값
- status: 작성됨 / 미기입 / 자료없음 / 확인 필요
- source: 고객 직접 입력 / 고객 파일 / 관리자 수정 / 시스템 계산
- touched: 고객이 실제로 입력하거나 선택했는지
- verified: 관리자가 원본과 대조했는지
- verifiedBy, verifiedAt
- version

placeholder와 예시값은 절대로 작성됨으로 판단하지 마.
고객 원문은 수정하지 않은 원본으로 별도 저장하고, 정규화된 관리자 필드는 복사본으로 만들어.
JSON 스키마, DB 테이블, 프런트엔드 검증 규칙, 자동저장과 제출 흐름을 구현해줘.
```

## 체크포인트

- 고객 원문과 정규화본이 분리됐는가
- placeholder가 작성됨으로 처리되지 않는가
- 필드별 출처와 검수 상태가 있는가
- 파일 항목도 자료없음과 자료있음으로 구분되는가
- 옵션·수치·인증이 구조화됐는가

# 4. 파일 이중 저장과 업체별 폴더링

## 설명

고객이 업로드한 원본은 서버 저장본과 고객 브라우저 IndexedDB 안전본으로 이중 저장합니다.

관리자 PC의 로컬 폴더는 작업 편의를 위한 동기화 대상이며 최종 원본 저장소로만 의존하지 않습니다.

## 프롬프트

```text
고객 업로드 파일의 이중 저장 시스템을 구현해줘.

저장 순서:

1. 고객이 파일을 선택하면 브라우저 IndexedDB에 임시 저장
2. 제출 시 HTTPS 업무 서버로 파일 전송
3. 서버는 비공개 객체 스토리지에 원본 저장
4. DB에는 파일 메타데이터와 객체 키만 저장
5. 서버 저장 성공 후 IndexedDB 상태를 동기화 완료로 변경
6. 실패하면 재전송 대기로 남기고 온라인 복구 시 재시도
7. 관리자는 로그인 후 파일 목록을 조회하고 서명 URL로 다운로드
8. 작업 폴더가 연결된 관리자 PC에서는 업체별 폴더로 복사

업체별 폴더 구조:

고객관리/
  업체명/
    프로젝트명/
      01_고객 작성 내용/
      02_제품 이미지/
      03_로고스펙 자료/
      04_참고 이미지/
      05_영상/
      06_인증 및 근거자료/
      07_기획안/
      08_Codex 작업 패키지/
      09_생성 시안/
      10_촬영 자료/
      11_디자인 작업물/
      12_수정 및 피드백/
      13_최종 납품/

조건:

- 파일명 충돌 시 덮어쓰지 말고 버전 추가
- SHA-256 해시로 중복 파일 확인
- MIME 타입과 확장자 검증
- 업로드 용량과 허용 형식 제한
- 악성 파일 검사 지점 마련
- 원본, 미리보기, 썸네일을 구분
- 삭제는 휴지통 보관 후 최고관리자 승인으로 영구삭제
- 고객 원본은 공개 GitHub 저장소에 포함하지 않기
- 서버와 IndexedDB 상태가 관리자 화면에서 구분되어 보이게 하기

DB 스키마, 객체 키 규칙, 재전송 큐, 폴더 동기화, 실패 복구 테스트까지 구현해줘.
```

## 체크포인트

- 서버와 IndexedDB에 이중 저장되는가
- 재전송 대기 상태가 있는가
- 다른 컴퓨터의 관리자가 파일을 볼 수 있는가
- 업체·프로젝트·자료 유형별 폴더가 자동 생성되는가
- 원본이 공개 저장소에 들어가지 않는가

# 5. 1차 제품 내용정리본 자동 생성

## 설명

고객 제출 직후 새로운 광고 문구를 만드는 것이 아니라, 고객이 준 사실을 빠짐없이 분류한 1차 내용정리본을 생성합니다.

불확실한 정보는 추정하지 않고 확인 필요로 남깁니다.

## 프롬프트

```text
고객 원문과 업로드 파일 메타데이터를 바탕으로 1차 제품 내용정리본 생성기를 만들어줘.

출력 양식:

1. 프로젝트 기본 정보
2. 제품명과 카테고리
3. 핵심 제품 정보
4. 옵션·구성·가격
5. 원재료·영양·원산지
6. 제조·인증·근거 정보
7. 핵심 장점과 고객 요청사항
8. 반드시 포함할 문구
9. 금지·주의 표현
10. 디자인 무드와 원하는 구성
11. 고객 업로드 파일 목록
12. 참고 링크
13. 미기입 항목
14. 자료없음 항목
15. 관리자 확인 필요 항목
16. 고객 원문 전문

규칙:

- 고객이 준 문장을 의미가 달라지게 요약하지 않기
- 숫자, 단위, 옵션, 품목보고번호를 원문 그대로 유지
- 인증과 효능은 증빙 상태를 함께 표시
- 서로 충돌하는 정보는 하나를 선택하지 말고 충돌 표시
- AI가 추정한 내용을 고객 작성값으로 기록하지 않기
- 내용정리본 JSON과 사람이 읽는 문서 두 가지로 저장
- 같은 입력으로 다시 생성하면 동일한 구조가 나오게 하기
- 원본 해시와 생성 버전을 기록하기

생성 로직, 출력 템플릿, 검증 테스트를 만들어줘.
```

## 체크포인트

- 원문이 누락 없이 보존되는가
- 미기입·자료없음·확인 필요가 분리됐는가
- 수치와 단위가 변형되지 않는가
- JSON과 읽기용 문서가 함께 생성되는가
- 입력 버전과 결과 버전을 추적할 수 있는가

# 6. 관리자 프로젝트 등록과 검수 잠금

## 설명

내용정리본이 생성되면 관리자 프로젝트 목록에 자동 등록합니다.

관리자가 필수 사실과 자료 상태를 검수하기 전에는 기획·이미지 생성 단계로 넘어갈 수 없어야 합니다.

## 프롬프트

```text
관리자 프로젝트 등록과 검수 승인 기능을 구현해줘.

목록 카드에 표시할 정보:

- 고객사명 / 제품명 / 접수일
- 프로젝트 상태
- 고객 작성 항목 체크
- 미기입 수
- 자료있음 / 자료없음
- 서버 저장 / IndexedDB 저장 상태
- 담당 관리자
- 검수 완료 여부
- 최근 수정일

불러오기를 누르면 고객 정리본을 관리자 입력 필드에 채워줘.
각 카테고리 옆에는 작성됨, 미기입, 확인 필요 상태를 과하게 튀지 않는 색으로 표시해줘.

검수 승인 조건:

- 고객사명
- 제품명
- 카테고리
- 한 줄 설명
- 핵심 제품 정보
- 고객 요청사항
- 반드시 포함할 문구
- 금지 표현
- 근거자료 상태

관리자가 승인하면 승인 시점의 스냅샷 해시를 저장해.
승인 이후 핵심 필드가 바뀌면 승인을 자동 해제하고 다시 검수하게 해.
미승인 상태에서는 기획/시안 자동 생성 버튼을 잠가.
모든 수정과 승인 기록을 감사 로그에 남겨줘.

페이지네이션, 검색, 필터, 담당자 배정, 삭제 확인창까지 실제 작동하게 구현하고 테스트해줘.
```

## 체크포인트

- 생략된 필드가 눈에 보이는가
- 승인 전 생성이 차단되는가
- 승인 후 핵심 수정 시 재승인이 필요한가
- 감사 로그가 남는가
- 프로젝트가 10개를 넘으면 페이지가 나뉘는가

# 7. 내부·Figma·외부 레퍼런스 라이브러리

## 설명

고객 DB만으로는 좋은 구성과 촬영 방향을 만들기 어렵습니다.

내부 최종 상세페이지, 제작 전 기획안, Figma 시안, Google Drive 자료, 고객 레퍼런스, 웹 검색 결과를 하나의 레퍼런스 카탈로그로 정리합니다.

레퍼런스는 복제 대상이 아니라 구성 방식과 사진 리듬을 분석하는 자료입니다.

## 프롬프트

```text
상세페이지 레퍼런스 라이브러리를 설계하고 구축해줘.

자료 출처:

- 내부에서 최종 제작한 상세페이지
- 제작 전 고객 안내용 기획안
- 포토그래퍼용 촬영 시안
- 승인된 Figma 상세페이지 시안
- Google Drive 레퍼런스 폴더
- 고객이 제출한 참고 링크와 이미지
- 네이버 스마트스토어, 쿠팡, 컬리, 자사몰 등 웹 검색 결과

각 레퍼런스에 저장할 정보:

- 출처와 URL 또는 파일 경로
- 사용 권한과 공개 가능 여부
- 업종, 제품 유형, 가격대, 타깃
- 전체 길이와 섹션 수
- 첫 화면 구조
- 설득 순서
- 사진 유형과 촬영 구도
- 색상, 여백, 타이포 위계
- 표·카드·비교 영역 사용 방식
- CTA 위치
- 참고 가능한 요소
- 복제하면 안 되는 고유 요소

웹 검색 시 최근 자료와 실제 판매 페이지를 확인하고 출처 URL을 남겨줘.
카피, 로고, 모델, 제품 사진, 고유 그래픽을 복제하지 말고 구조적 특징만 추출해.
레퍼런스를 업종·소구 유형·무드·사진 방식으로 검색할 수 있게 인덱싱해줘.

프로젝트마다 관련도가 높은 레퍼런스를 추천하되 추천 이유를 표시하고, 관리자가 최종 선택하게 해줘.
```

## 체크포인트

- 내부 제작물과 외부 참고물이 구분되는가
- 사용 권한 정보가 있는가
- 검색 결과에 출처가 남는가
- 고유 디자인을 복제하지 않는가
- 프로젝트별 추천 이유가 표시되는가

# 8. 기획안과 A/B 방향 자동 생성

## 설명

승인된 내용정리본과 선택된 레퍼런스를 바탕으로 고객·포토그래퍼·디자이너가 함께 이해할 수 있는 제작 전 기획안을 만듭니다.

A안과 B안은 색만 다른 시안이 아니라 설득 전략 자체가 달라야 합니다.

## 프롬프트

```text
승인된 프로젝트 스냅샷과 선택된 레퍼런스를 기반으로 상세페이지 제작 전 기획안을 생성해줘.

A/B 방향:

- A안: 브랜드 감성, 프리미엄 첫인상, 원료와 사용 장면 중심
- B안: 제품 장점, 근거, 비교, 구매 판단 정보 중심
- 제품 특성에 따라 더 적절한 방향을 추천하고 추천 근거를 점수와 문장으로 표시

기획안에 포함할 항목:

- 프로젝트 요약
- 핵심 타깃과 구매 고민
- 핵심 구매 이유
- A안/B안의 설득 전략 차이
- 권장 상세페이지 길이와 섹션 수
- 상단·중단·하단 구성
- 섹션별 목적
- 섹션별 메인카피 초안
- 사용할 고객 자료
- 추가로 필요한 자료
- 확인되지 않은 표현
- 촬영이 필요한 장면
- 디자이너가 정확히 조판해야 할 문구와 표
- 모바일 가독성 기준
- 예상 제작 범위와 바리에이션 여부

규칙:

- 고객이 제공하지 않은 옵션과 효능을 만들지 않기
- 근거 없는 리뷰와 평점을 생성하지 않기
- 경쟁사 표현을 그대로 사용하지 않기
- 작은 한글을 이미지 픽셀에 굽는 대신 조판 영역으로 표시
- 고객용 설명과 내부 제작 지시를 분리
- 기획안 HTML, PDF용 문서, JSON을 함께 생성

관리자가 A/B 중 하나를 선택하기 전에는 이미지 시안 생성 작업을 잠가줘.
```

## 체크포인트

- A안과 B안의 전략이 실제로 다른가
- 추천 근거가 있는가
- 고객·포토그래퍼·디자이너가 각각 필요한 정보를 얻는가
- 확인되지 않은 사실이 분리됐는가
- 관리자 선택 전 이미지 생성이 잠기는가

# 9. 촬영 레퍼런스와 컷 리스트 생성

## 설명

상세페이지 시안 안의 이미지는 단순 장식이 아니라 포토그래퍼가 어떤 사진을 찍어야 하는지 알려주는 촬영 레퍼런스 역할을 해야 합니다.

제로베이스 프로젝트에서는 제품 누끼가 없어도 필요한 구도와 조명을 먼저 제안해야 합니다.

## 프롬프트

```text
승인된 기획안으로 포토그래퍼용 촬영 레퍼런스 보드와 컷 리스트를 만들어줘.

각 컷에 포함할 정보:

- 컷 번호
- 들어갈 상세페이지 섹션
- 촬영 목적
- 필수 피사체
- 제품 방향과 크롭
- 카메라 앵글과 렌즈 느낌
- 배경과 소품
- 조명 방향과 그림자
- 색온도와 보정 무드
- 세로·가로 비율
- 카피가 들어갈 안전 여백
- 누끼 필요 여부
- 합성 가능 여부
- 촬영 우선순위
- 대체 가능한 이미지 생성 시안

필요한 컷 유형:

- 히어로 제품 컷
- 정면·측면·후면 패키지
- 스케일 확인 컷
- 원료 또는 소재 컷
- 사용 장면
- 디테일 확대
- 구성품과 옵션
- 비교 또는 기능 설명용 컷
- 하단 제품 정보용 정확한 정면 컷

제품 원본이 없으면 가상의 패키지를 최종 제품처럼 만들지 말고, 자리·구도·빛·여백을 보여주는 촬영 가이드 이미지로 표시해.
모든 생성 이미지는 “촬영 레퍼런스” 워터마크 또는 메타데이터를 갖게 해.
촬영 시안보드 HTML, 컷 리스트 CSV, 이미지 생성 지시문을 함께 저장해줘.
```

## 체크포인트

- 섹션과 촬영 컷이 연결되는가
- 카피 안전 여백이 표시되는가
- 제로베이스 제품을 확정 패키지처럼 만들지 않는가
- 촬영 목적과 우선순위가 있는가
- 포토그래퍼가 바로 이해할 수 있는가

# 10. OpenAI API 없는 Codex 작업 패키지

## 설명

관리자툴의 버튼은 OpenAI API를 직접 호출하지 않습니다.

대신 승인된 DB, 선택 레퍼런스, 기획안, 촬영 계획을 하나의 작업 패키지로 만들고 Codex가 실행할 수 있는 명확한 지시서와 폴더를 생성합니다.

## 프롬프트

```text
OpenAI API를 사용하지 않는 Codex 작업 패키지 생성 기능을 구현해줘.

관리자가 “Codex 작업 준비” 버튼을 누르면 아래 파일을 생성해.

- job.json: 프로젝트 ID, 승인 스냅샷 해시, 선택 A/B안, 출력 목록
- customer_facts.json: 승인된 고객 사실만 포함
- missing_and_unverified.json: 미기입과 확인 필요 항목
- references.json: 선택된 레퍼런스와 사용 가능 범위
- planning_brief.md: 상세페이지 기획안
- shot_list.csv: 촬영 컷 리스트
- image_tasks.md: 생성할 이미지별 프롬프트
- final_page_spec.md: 최종 상세페이지 규격과 조판 지시
- RUN_WITH_CODEX.md: Codex에서 실행할 마스터 지시문

중요 조건:

- API 키 입력란을 만들지 않기
- api.openai.com 호출 코드를 만들지 않기
- 고객 비밀번호와 관리자 세션을 패키지에 넣지 않기
- 고객 원본은 파일 복사 대신 권한이 있는 로컬 경로 또는 안전한 다운로드 절차로 연결
- 패키지마다 승인 해시와 버전 기록
- Codex 실행 전 패키지 무결성 검사
- 실행 결과는 result-manifest.json으로 기록
- 실패한 작업만 재실행할 수 있게 작업 단위를 분리
- Codex가 생성한 파일은 업체별 결과 폴더에 저장
- 관리자툴은 result-manifest.json을 읽어 진행 상태와 결과 링크를 표시

현재 Codex 계정 사용량을 일반 웹앱의 서버 재화처럼 직접 호출할 수 있다고 가정하지 마.
1차 버전은 관리자가 Codex에서 RUN_WITH_CODEX.md를 실행하는 반자동 방식으로 완성해.
추후 공식 계정 기반 자동 실행 방식이 확인됐을 때만 무인 실행 어댑터를 별도 모듈로 추가해.
```

## 체크포인트

- OpenAI API 호출이 완전히 제거됐는가
- 승인된 DB만 패키지에 들어가는가
- Codex 실행 지시가 한 파일로 정리되는가
- 결과 manifest를 관리자툴이 다시 읽는가
- 실패 작업만 재실행할 수 있는가
- 존재하지 않는 무인 Codex 호출 기능을 가장하지 않는가

# 11. Codex 이미지 생성과 상세페이지 시안 제작

## 설명

Codex에서 작업 패키지를 실행하면 이미지 생성 기능을 사용해 상세페이지 방향성 시안과 촬영 레퍼런스를 만듭니다.

긴 상세페이지를 한 장에 무리하게 생성하지 않고 섹션 단위로 생성한 뒤 일관성을 검수합니다.

## 프롬프트

```text
첨부된 Codex 작업 패키지를 읽고 상세페이지 이미지 시안을 생성해줘.

실행 순서:

1. job.json과 승인 해시 확인
2. 고객 사실과 미확인 항목 분리
3. 선택된 기획 방향 확인
4. 제품 원본, 로고, 패키지, 레퍼런스 확인
5. 섹션별 이미지 생성
6. 섹션 간 제품 비율, 조명, 색감, 여백 일관성 검사
7. 촬영 레퍼런스와 상세페이지 시안을 구분해 저장
8. 생성 실패 시 해당 섹션만 재시도
9. 결과 이미지, 사용 프롬프트, 검수 결과, 실패 로그 저장
10. result-manifest.json 갱신

이미지 생성 규칙:

- 고객 제품 외형, 로고, 패키지 색과 비율을 임의로 변경하지 않기
- 실제로 없는 옵션, 맛, 구성품, 인증 마크를 만들지 않기
- 제품 원본이 없으면 촬영 가이드용 임시 비주얼임을 명확히 표시
- 상단, 핵심 장점, 근거, 사용 장면, 상세 정보, 구매 판단 순서를 유지
- 작은 한글, 표, 영양정보, 법정 고지는 이미지에 확정 텍스트로 굽지 않기
- 정확한 텍스트 조판을 위한 안전 영역 남기기
- 모바일 축소 화면에서 제품과 핵심 카피가 먼저 보이게 하기
- 레퍼런스의 고유 카피와 디자인을 복제하지 않기
- 각 이미지가 촬영자와 디자이너에게 실제 작업 지시가 되게 하기

출력 폴더에 섹션별 PNG, 전체 미리보기, 프롬프트, QA 보고서, README를 저장해줘.
```

## 체크포인트

- 섹션별 이미지와 전체 미리보기가 있는가
- 실패 섹션만 재생성되는가
- 촬영 레퍼런스와 고객용 시안이 구분되는가
- 정확한 텍스트를 위한 안전 영역이 있는가

# 12. 최종 상세페이지 제작물 조립

## 설명

방향성 시안이 승인되면 실제 촬영물과 정확한 문구를 사용해 최종 상세페이지 제작물로 조립합니다.

AI 이미지에 들어간 임시 문구를 그대로 납품하지 않고 디자이너 조판과 내부 검수를 통과해야 합니다.

## 프롬프트

```text
승인된 상세페이지 시안, 실제 촬영 이미지, 고객 확정 문구를 사용해 최종 상세페이지 제작 구조를 만들어줘.

기본 제작 규격:

- 기획 + 디자인: 기본 10,000px
- 추가 분량: 5,000px 단위
- 디자인만 진행하는 프로젝트와 기획 포함 프로젝트 구분
- 동일 디자인 바리에이션은 원본 프로젝트와 연결
- PSD 원본 제공 여부 기록

제작 조건:

- 실제 촬영물과 승인된 고객 원본을 우선 사용
- 제품 정보, 원재료, 영양표, 인증번호, 주의사항은 정확한 텍스트 레이어로 조판
- 모바일에서 읽을 수 있는 최소 글자 크기와 행간 적용
- 섹션별 편집 가능한 원본과 전체 미리보기 생성
- 임시 이미지, 촬영 대기 이미지, 확정 이미지를 상태로 구분
- 고객 승인 전 최종 납품 상태로 변경하지 않기
- 원본 파일, 웹용 이미지, 썸네일, QA 보고서를 분리
- 바리에이션은 공통 레이아웃과 변경된 데이터의 차이를 기록
- 최종 파일에 프로젝트 ID와 버전 메타데이터 포함

완성품을 자동으로 무검수 납품하지 말고 디자이너 검수, 내부 QA, 고객 컨펌 단계를 반드시 유지해줘.
```

## 체크포인트

- 촬영 시안이 실제 촬영물로 교체됐는가
- 정확한 문구가 텍스트 레이어로 들어갔는가
- 편집 원본과 웹용 결과가 분리됐는가
- 바리에이션 변경 이력이 있는가
- 사람 검수 없이 납품되지 않는가

# 전체 구현을 시작할 때 사용하는 마스터 프롬프트

```text
넌 상세페이지 제작 자동화 시스템을 구축하는 시니어 풀스택 엔지니어, AI 워크플로 설계자, 상세페이지 기획자야.

10. 보안, 복구, 테스트, 배포 문서 완성

- 고객 사실보다 레퍼런스를 우선하지 않는다.
- 다른 업체의 상세페이지를 복제하지 않는다.
- 이미지 시안과 최종 납품물을 구분한다.
- 원본 문서, 고객 이미지, 비밀번호, 세션, 비밀값을 공개 GitHub에 올리지 않는다.
```

# 권장 실행 순서

각 단계의 프롬프트를 한 번에 모두 입력하지 말고 아래 묶음으로 진행합니다.

- 1차: 1~4단계 — 구조, 로그인, DB, 파일 저장
- 2차: 5~6단계 — 내용정리본, 관리자 검수
- 3차: 7~9단계 — 레퍼런스, 기획안, 촬영 시안
- 4차: 10~12단계 — Codex 작업 패키지, 이미지 생성, 최종 제작
- 5차: 13~15단계 — 고객 피드백, 안정화, 배포

각 묶음이 끝날 때 실제 화면 테스트, 데이터 보존 테스트, 다른 컴퓨터 접속 테스트, 권한 테스트를 통과한 뒤 다음 단계로 넘어갑니다.
